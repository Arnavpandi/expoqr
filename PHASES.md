# Expo QR Registration System — 5 Phases

## Phase 1 — Database Setup (Supabase)

Run `supabase/schema.sql` once in the Supabase dashboard → **SQL Editor**:

```sql
create table if not exists public.visitors (
  id uuid primary key default gen_random_uuid(),
  created_at timestamptz not null default now(),
  name text not null,
  phone text not null unique,
  company text,
  occupation text,
  qr_token uuid not null unique default gen_random_uuid(),
  checked_in boolean not null default false
);

create index if not exists idx_visitors_qr_token on public.visitors (qr_token);
create index if not exists idx_visitors_checked_in on public.visitors (checked_in);

-- RLS: enabled, NO grants to anon/authenticated. The Next.js API routes and
-- scripts/feedback.mjs use the service-role key, which bypasses RLS.
-- Visitors have no direct row access — every write goes through the backend.
alter table public.visitors enable row level security;
```

## Phase 2 — Next.js Backend: `POST /api/register`

`app/api/register/route.ts` (TypeScript):

1. **Extract** the JSON payload: `{ name, phone, company, occupation }`.
2. **Normalize** the phone to digits-only (`normalizePhone` in `lib/waha.ts`),
   then call the WAHA endpoint (verified against the WAHA docs):
   ```
   GET {WAHA_URL}/api/contacts/check-exists?phone=<digits>&session=<session>
   Header: X-Api-Key: <WAHA_API_KEY>
   → { "numberExists": true, "chatId": "…@c.us" }
   ```
3. **If invalid** (`numberExists: false`) → `400 { error: "Not a valid WhatsApp number" }`.
4. **If valid** → insert into `visitors` via the service-role Supabase client
   (`lib/supabase.ts`); `qr_token` is generated by the DB default
   (`gen_random_uuid()`).
5. **Return** `201 { qr_token, name }`. Duplicate phone → `409`
   (unique-violation `23505` mapped to a friendly message).

WAHA outage → `502` with a retry-friendly message (never registers unverified).

## Phase 3 — Frontend: `/` registration page

`app/page.tsx` — mobile-optimized Tailwind form (`name`, `phone` with country
code, `company`, `occupation`):

- Submitting → button shows "Verifying WhatsApp number…", form disabled.
- API error → red alert box with the server's message, form stays visible.
- Success → form is hidden and a **digital badge** renders: the returned
  `qr_token` as a QR code (`react-qr-code`), the visitor's name, and the text
  **"Take a screenshot to show at the gate."**

## Phase 4 — Volunteer scanner: `/scan` + `POST /api/checkin`

`app/scan/page.tsx` (hidden route — share the link with volunteers only):

- Uses `html5-qrcode` to open the phone's rear camera (`facingMode:
  "environment"`) and decode QR codes continuously.
- Each decoded `qr_token` auto-calls `POST /api/checkin { qr_token }`
  (`app/api/checkin/route.ts`), which validates the UUID, looks the visitor up,
  and sets `checked_in = true`.
- Feedback per scan: **green "CHECKED IN ✓"** (+ visitor name, beep 880 Hz),
  **amber "ALREADY CHECKED IN"** (idempotent — no double count), **red
  "UNKNOWN BADGE"** (404) or "SCAN ERROR". A counter tracks check-ins this
  session. A 1.2 s cooldown prevents the same badge double-firing while the
  camera keeps decoding.

## Phase 5 — Post-event feedback script

`scripts/feedback.mjs` — standalone Node 18+ script (no dependencies):

1. `GET {SUPABASE_URL}/rest/v1/visitors?select=id,name,phone&checked_in=eq.true`
   with the service-role key.
2. For each visitor, POST to WAHA (verified against the WAHA docs):
   ```
   POST {WAHA_URL}/api/sendText
   Header: X-Api-Key: <WAHA_API_KEY>
   Body: { "session": "<session>", "chatId": "<digits>@c.us", "text": "Hi [Name], thanks for visiting our expo! Reply with a number from 1 to 5 to rate your experience." }
   ```
3. Random **3–6 second delay** between sends (human-like pacing, avoids spam
   flags); per-recipient success/failure log; exits non-zero if any send failed.

Run: `npm run feedback` (with env vars exported, or `source .env.local` first).
